### OBS-2a — Conversation attribution (M, partial by design)

**MCP carries no conversation identifier.** No revision, including 2026-07-28, defines one. External hosts (Claude Desktop, Claude Code, VS Code Copilot, Antigravity) therefore cannot tell the server which of their threads a call belongs to. Attribution below the app level is possible **only for clients this repo controls**.

| # | Acceptance criterion | Test |
| :-- | :--- | :--- |
| 2a.1 | The web agent injects its conversation id into `_meta` (OpenTelemetry `baggage`, per the spec's `_meta` trace-context conventions) on every call | `test_mcp_client` |
| 2a.2 | The gateway logs that id into the audit record as `conversation_id` | `test_observability` |
| 2a.3 | An Audit Log row sourced from `control-room` links to the originating saved conversation | component test |
| 2a.4 | A row from any other source shows `conversation = n/a`, not a blank and not a guess | component test |
| 2a.5 | The UI never groups calls into an inferred "conversation" for external hosts — time-clustering may aid reading, but must never be labelled as a thread identity | component test |
| 2a.6 | `conversation_id` is treated as opaque; no user content is placed in `_meta` | code review |

**Why no protocol version solves this.** The 2026-07-28 `_meta` reserved-key registry is `progressToken`, `io.modelcontextprotocol/protocolVersion`, `/clientInfo`, `/clientCapabilities`, `/logLevel`, `/subscriptionId`, and the OpenTelemetry trio `traceparent` / `tracestate` / `baggage`. None carries a conversation, thread, or chat identity, and no earlier revision did either. The `Mcp-Session-Id` header of `2025-11-25` and earlier identified a **connection**, not a conversation — a host typically holds one connection across all of its chats. The current spec forbids the substitution outright: a connection "is not a conversation or session … a server must not treat connection or process identity as a proxy for conversation or session continuity." **Downgrading the protocol to obtain a session id would lose per-request `clientInfo` — and therefore per-call app attribution — while still not answering "which chat".** Do not propose it.
